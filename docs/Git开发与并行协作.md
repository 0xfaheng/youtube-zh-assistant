# Git 开发与并行协作

## 一个聊天怎样对应一个任务

聊天是沟通记录；Git 分支保存该任务的提交；worktree 是该任务实际修改的独立目录。一个任务用一个分支和一个 worktree，可以用一个或多个接续聊天，但同一目录同时只能有一个修改者。新开聊天并不会自动隔离文件。

默认保留一个主聊天负责需求拆分、合并、版本号、发布和正式服务。清晰且独立的任务可以开新聊天并行；涉及同一接口或共享状态时先协调，必要时串行执行。

本地顺序工作不需要为每个小步骤开聊天；在原任务聊天继续最省上下文。只有独立新目标才新建任务；上下文太长时，新聊天继续原目录、原分支，先读取提交与任务说明。

## 创建一个任务

在主工作目录 `E:\YouTube中文插件开发` 的 PowerShell 中执行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\new-task.ps1 -Name subtitle-layout -Type fix
```

工具要求 main 工作区干净，创建 `fix/subtitle-layout` 和独立目录 `E:\YouTube中文插件开发-worktrees\subtitle-layout`，输出起点提交。重复任务名会拒绝；它不会覆盖目录或自动丢弃修改。

在 Codex 创建聊天时选择 Git worktree 环境（适用于项目已被识别为 Git 仓库的情况），或者把工具输出的任务目录作为该聊天的项目/工作目录。两种方式选一种，不需要重复创建 worktree。不同聊天不能都指向主目录。开始时要求助手报告实际 cwd 和分支；路径未隔离就先停止修改，不能仅凭聊天标题判断隔离成功。

新任务提示词示例：

> 在这个项目为“修复字幕排版”创建独立 worktree 和任务分支，从 main 开始。先报告实际工作目录、分支和起点提交。目标是……；只负责 extension/content.js 与相关测试，其他文件变更先说明。阅读根目录 AGENTS.md，完成修改和相关测试后提交，报告提交号、验证结果、接口变化和未完成事项，交给主聊天统一合并。真实服务、版本号和打包由主聊天负责。

如果已用脚本创建目录，将第一句替换为“在 `E:\YouTube中文插件开发-worktrees\subtitle-layout`、`fix/subtitle-layout` 接续工作，不再创建第二个 worktree”。另一种做法是在主聊天直接要求创建独立子任务 worktree；由主聊天提供目录后再开聊天。新聊天是否已在正确目录，以实际检查为准。

## 日常提交与合并

1. 修改前检查 `git status --short --branch` 和 `git log -3 --oneline`。出现意外修改时先弄清来源。
2. 只修改本任务负责的文件；主仓库和其他任务目录不是写入目标。不要执行旧 `work/` 中硬编码主项目路径的升级脚本。
3. 每完成一个完整改动，检查 `git diff`，运行相关测试，明确列出文件执行 `git add -- <文件>`，再 `git commit -m "fix: 修复字幕排版并补充回归验证"`。重要未完成工作也保存检查点，并在提交说明中标注尚未验收。
4. 任务聊天报告分支、提交号、验证结果和未完成事项；主聊天先检查 diff，在干净 main 上执行 `git merge --no-ff fix/subtitle-layout`。冲突需要结合两边意图解决，不直接用一边覆盖另一边。
5. 合并后运行相关测试；跨模块改动运行完整 `npm test`，必要时安排集成测试，然后备份仓库。不要把“分支测试通过”当成“合并后的代码已经通过”。

`git add .` 之前必须核对状态，不把未知文件一起提交。Git 没有记录每次保存的自动功能；只有已提交状态和 Git 已保存的对象能提供可靠历史。未跟踪或被忽略的文件不受 Git 回退保护。

任务结束后可以保留 worktree 以便继续。确定已合并、已备份且没有未提交内容后，再从主目录执行 `git worktree remove <任务目录>`。Codex 管理的 worktree 优先用应用提供的归档工具，不直接递归删除目录。分支删除在核对合并状态后进行，不强制删除未合并分支。

## 并行测试的实际边界

本轮没有修改插件运行功能。当前 server/main.mjs 与 start/stop 脚本仍使用正式端口 `17865`；任务 worktree 不得启动或停止这套正式服务，不得复用正式配对码。可以在自己的目录运行单元测试和随机端口模拟服务，产物写本 worktree 的 work/ 或系统临时目录。

浏览器、真实账号翻译和 GPU 识别测试由主聊天安排独占时段。日常 Chrome 沿用独立启动规则。以后若需要两个完整实例同时测试，单独开发并验证端口、运行目录、插件服务地址、浏览器资料和 GPU 调度配置；仅创建 worktree 不会自动解决这些共享资源。

## 统一发布

只有主聊天发布。沿用原有开发记录、版本一致性、验证和哈希要求，流程如下：

1. 合并任务，统一升级版本号，完成全部必要验证和 `开发记录/v<版本>.md`，更新索引与 CHANGELOG。
2. 提交源码、记录和测试证据，确认 main 工作区干净。所有将进入完整包的文件都必须受 Git 跟踪；ignored 文件混入源码目录会被拒绝。
3. 可先运行 `node work/package-release.mjs --check`，它只做开发记录、版本和 Git 检查。再执行正式打包；版本标签或同版本 ZIP/RAR 已存在会拒绝覆盖。
4. 打包报告保存 `sourceCommit`，表示打包前经过验证的代码起点。核验 ZIP/RAR、解包文件及 SHA-256，把本轮最终打包报告和哈希清单复制到 `verification/releases/<版本>/` 保存。外部安装包哈希文件仍保留原处。
5. 打包会更新受跟踪的 `verification/package-report.json`，需要将最终报告/清单提交为发布证据，再创建附注标签 `git tag -a v<版本> -m "发布 v<版本>，验证与安装包哈希已保存"`。最终标签与 report.sourceCommit 可以不同：二者之间仅允许最终发布证据变更，不能再改变产品源码；若源码有变化，旧包不能作为交付结果。
6. 执行 Git 备份，再由主聊天根据现有安全规则升级正式服务、同步或重载插件，报告实际验证范围。不要让多个任务同时改版本、打包、停止或启动服务。

如果打包中途失败，保留失败证据，核对产物。当前工具会拒绝覆盖部分存在的包；将本次失败产物移入独立失败归档后再重试，不能删除或覆盖已有正式版本。`v0.4.7` 为已交付导入基线，不能直接重打本版覆盖旧包。

## 查历史、撤销与运行回退

```powershell
git log --oneline --decorate -15
git diff v0.4.7..main -- outputs/youtube-zh-assistant/extension
git show <提交号> -- <文件路径>
```

已经合并到 main 的错误改动，用 `git revert <提交号>` 新建撤销提交，再验证。撤销 merge commit 需要明确主线，例如 `git revert -m 1 <合并提交号>`，先核对父提交；不要盲目撤销。

查看旧版代码，可以执行 `git worktree add --detach E:\YouTube中文插件开发-worktrees\inspect-047 v0.4.7`，在单独目录查看。它不会启动服务或恢复运行配置。运行版本回退需先停止采音、确认队列空闲，使用现有安全脚本停止服务，按开发记录用旧完整包恢复代码，保留运行配置与密钥，再启动旧服务并重载扩展；不能在正在运行的正式源码目录随意切版本。

不要擅自执行 `reset --hard`、`clean -fd`、强制推送或移动历史标签。若其他任务尚未合并，回退前告知主聊天评估影响。

## 备份与恢复

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\backup-git.ps1
```

默认写入 `C:\Users\Administrator\.codex\project-backups\youtube-zh-assistant`，每次新建带上海时间戳的 bundle 与 SHA-256 元数据，校验 bundle。可用 `-Destination <目录>` 指定外接盘等位置。本机另一卷仍不能代替异机或离线备份。

bundle 包含所有已提交分支与标签；不包含未提交文件、被忽略的配对码/配置、安装包或模型。安装包、必要运行配置要另行保存。恢复到新目录：

```powershell
git clone -b main <完整bundle路径> E:\译幕-Git恢复
git -C E:\译幕-Git恢复 fsck --full
```

需要恢复其他任务分支时，从 bundle clone 后的 `origin/<分支>` 创建本地分支，再重建 worktree。不要用恢复命令覆盖现有项目。Git 能保存配置恢复工具，不能自动恢复被忽略的实际配置和密钥。

本次没有创建 GitHub 仓库或配置远程推送。以后可单独配置私有远程仓库和备份策略，先核对账号、权限和提交内容。

## Agent 开发补充规范

本节专门说明使用 Agent 开发时最容易误解的地方。聊天、Agent、分支和 worktree 需要分别管理；不要把其中任何一个概念当成另一个概念。

### 先记住六条规则

1. **新聊天不等于新分支。** 新建聊天只会新建沟通窗口，不会自动创建 Git 分支。
2. **新分支不等于新目录。** 如果两个分支被检出到同一个目录，两个 Agent 仍然可能互相覆盖。
3. **并行开发必须同时隔离分支和 worktree。**
4. **一个独立目标一个任务分支。** 同一个任务可以有多个提交和多个接续聊天。
5. **main 只用于集成和发布。** 功能、修复和实验默认在任务 worktree 完成。
6. **只有 commit 才是可靠回溯点。** 聊天记录、未保存文件、未跟踪文件和被忽略文件不能代替 Git 历史。

### 四个对象分别负责什么

| 对象 | 作用 | 是否会自动产生 |
| --- | --- | --- |
| 聊天 | 保存需求、决策、测试结论和交接信息 | 新开聊天时产生 |
| Agent | 执行读取、修改、测试和提交 | 由聊天或任务调度启动 |
| 分支 | 保存一条独立的提交历史 | 需要显式创建 |
| worktree | 给分支提供独立的实际文件目录 | 需要显式创建或选择 Codex worktree |

正确的并行单位是：

~~~text
一个独立任务 = 一个聊天 + 一个任务分支 + 一个任务 worktree + 明确文件责任
~~~

可以有多个聊天接续同一个任务，但这些聊天必须使用同一个任务 worktree 和同一个任务分支。不要因为换了聊天就重新创建一条相同任务的分支。

### Agent 与传统手写开发的区别

传统手写开发通常由一个人直接控制一个目录，开发者知道哪些窗口正在修改什么。Agent 开发会增加三类风险：

- 多个聊天可能指向同一个目录；
- Agent 能读到 Git 状态，却不能可靠推断另一个聊天的意图；
- Agent 能执行命令，范围不清时可能误启动服务、修改版本或加入临时文件。

因此 Agent 开发必须多做三件事：

1. 开始前报告实际 cwd、分支、起点提交和工作区状态；
2. 开始前明确目标、负责文件、禁止触碰的共享资源和验收条件；
3. 结束时提交或报告未提交原因、测试结果、未完成事项和风险。

Agent 是执行者，不是默认的项目管理员。除非提示词明确要求并且当前目录正确，Agent 不应自行合并、发布、重启正式服务、读取配对码、修改其他任务或删除用户修改。

### 哪些动作不会自动发生

以下动作不能仅靠新开聊天或聊天标题完成：

- 不会自动创建分支；
- 不会自动创建独立目录；
- 不会自动判断是继续旧任务还是开始新任务；
- 不会自动发现另一个聊天正在修改同一个文件；
- 不会自动把其他聊天的提交合并到当前分支；
- 不会自动解决冲突；
- 不会自动隔离端口、配对码、GPU、浏览器资料和运行目录；
- 不会自动把 ZIP、RAR、运行配置和密钥放入备份。

Codex 可以在明确选择 Git worktree 环境时创建独立 worktree，也可以在主聊天明确协调下执行 Git 操作。但必须检查工具返回的实际路径和分支，不能只相信聊天标题或界面名称。Git 本身不会因为 Agent 之间有多个聊天就自动合并。

## 新开聊天应该怎么做

### 继续同一个任务

如果目标没有变化，优先继续原聊天，最省 token。如果原聊天过长，需要换聊天，必须提供原 worktree 和原分支：

~~~text
请继续已有任务，不要创建新分支。

工作目录：E:\YouTube中文插件开发-worktrees\subtitle-layout
分支：fix/subtitle-layout

请先执行 git status --short --branch、git log -3 --oneline 和 git worktree list，读取 AGENTS.md 及已有任务说明。先报告实际 cwd、分支、未提交文件和最近提交，不要 reset、clean、覆盖或删除已有修改。
~~~

### 开始一个新的独立任务

先在主仓库创建任务分支和 worktree：

~~~powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\new-task.ps1 -Name audio-capture -Type feat
~~~

再把工具输出的目录和分支交给新聊天：

~~~text
这是一个新的独立任务，请只在以下目录工作：

工作目录：E:\YouTube中文插件开发-worktrees\audio-capture
分支：feat/audio-capture

先报告实际 cwd、当前分支、起点提交和 git status，阅读根目录 AGENTS.md 与 docs/Git开发与并行协作.md。

目标：……
负责文件：……
验收条件：……
禁止事项：不修改其他任务，不改版本号和发布包，不使用正式配对码，不启动正式服务。

完成后运行相关测试，提交 Git，并报告提交号、测试结果、未完成事项和风险。
~~~

如果 Codex 创建聊天时已经选择了 Git worktree，就不要再运行 new-task.ps1。二选一即可，否则可能创建两个不同目录，导致你以为 Agent 在同一份代码上工作，实际却不在同一个 worktree。

### 只做审查的新聊天

审查聊天可以只读，不需要新分支：

~~~text
请只审查分支 fix/subtitle-layout 相对 main 的差异。
工作目录：……
不要修改文件、不要提交、不要合并、不要启动服务。
请报告高风险问题、测试缺口和具体文件位置。
~~~

审查聊天也要指定目录和范围。只读审查通常可以与开发聊天并行。

### 负责集成的新聊天

只有主聊天或明确授权的集成聊天可以执行合并：

~~~text
请在主仓库执行集成检查。
先确认 main 干净，读取任务分支的提交、diff、测试结果和未完成事项。
先报告冲突、接口变化和合并顺序，再执行合并；合并后运行相关回归测试。
~~~

## 三种工作模式

| 情况 | 聊天 | 分支和目录 | 处理方式 |
| --- | --- | --- | --- |
| 同一个任务继续改 | 原聊天或接续聊天 | 原分支、原 worktree | 继续开发并提交 |
| 新的独立目标 | 新聊天 | 新分支、新 worktree | 独立测试，交主聊天合并 |
| 两个任务并行 | 两个聊天 | 两个分支、两个 worktree | 各自完成，主聊天统一集成 |

不建议每个小修改新开聊天，也不建议两个聊天共享一个 worktree。前者浪费上下文，后者容易覆盖代码。

## Agent 启动检查

每个任务 Agent 开始修改前都应执行：

~~~powershell
git rev-parse --show-toplevel
git status --short --branch
git log -3 --oneline --decorate
git branch --show-current
git worktree list
~~~

必须确认：

1. 实际 cwd 是任务目录，不是主仓库目录；
2. 当前分支是提示词指定的任务分支；
3. 起点提交符合任务要求；
4. 没有来源不明的未提交修改；
5. 没有另一个 Agent 使用同一 worktree。

发现目录或分支不对时，Agent 应停止写入并报告，不能自行猜测、reset 或切换到另一个目录。

## 任务卡与文件责任

每个独立任务使用一张短任务卡，不要把整个项目历史复制到聊天里：

~~~text
任务名：字幕排版修复
目标：解决长句在双行字幕中的断行错误
起点：main 的 f1bdb90
分支：fix/subtitle-layout
目录：E:\YouTube中文插件开发-worktrees\subtitle-layout
负责文件：extension/content.js、extension/tests/content.test.cjs
不负责：版本号、CHANGELOG、打包、正式服务
验收：相关测试通过；不改变短字幕现有行为
交付：提交号、测试命令、测试结果、未完成事项
~~~

文件责任不是绝对禁止跨文件修改。如果实现确实需要改变接口，Agent 应先说明扩大范围，并把相关测试一并纳入提交。不要静默顺手格式化或重写无关文件。

## 提交规则

完成一个有意义的小阶段后：

~~~powershell
git diff --stat
git diff -- <相关文件>
npm test --prefix outputs/youtube-zh-assistant
git add -- <明确的文件列表>
git commit -m "fix: 修复长字幕断行并补充回归测试"
~~~

不要默认使用：

~~~powershell
git add .
git reset --hard
git clean -fd
git push --force
git tag -f
~~~

提交可以有多个，但不要长时间积累大量未提交内容。重要的未完成阶段也可以提交检查点，但报告中必须写明“未验收”或“仅保存检查点”。

建议提交类型：

~~~text
feat: 增加音频采集状态提示
fix: 修复长字幕断行
test: 补充配对失败回归测试
docs: 更新 Agent 协作规范
chore: 调整发布检查
~~~

## 两个 Agent 并行时的边界

两个任务可以同时工作，但必须满足：

- 不在同一个目录修改；
- 不同时修改同一共享接口，除非已经约定接口；
- 不同时修改版本号、CHANGELOG、开发记录索引和安装包；
- 不同时启动正式服务；
- 不共享会被写入的临时输出目录；
- 不擅自把对方提交 cherry-pick、merge 或 reset 到自己的分支；
- 各自完成测试和提交，再交主聊天统一合并。

如果两个任务必须修改同一个文件，优先改为串行。读密集任务适合并行，写密集任务必须按文件或模块分配唯一负责人。

## 主聊天和任务聊天的责任

主聊天负责拆任务、决定是否并行、检查目录、收集提交、处理冲突、合并 main、运行合并后测试、统一版本发布、安排正式服务和真实集成测试。

任务聊天负责自己的目标、文件和测试，提交代码并做交接报告。任务 Agent 不负责最终版本号、打包、正式服务重启或安装包发布。

任务结束报告至少包括：

~~~text
工作目录：……
分支：……
起点提交：……
完成提交：……
改动文件：……
测试命令与结果：……
未完成事项：……
风险和需要主聊天处理的内容：……
~~~

## 在 main 上直接改代码

本项目默认不在 main 上直接开发功能。main 是集成和发布线。

只有集成、协作文档或发布记录这类小改动，且没有其他任务正在合并时，才可以直接在 main 做并立即提交。产品功能和 bug 修复应当进入任务分支。

如果 Agent 已经误在 main 上改了产品代码：

1. 停止继续修改；
2. 检查 git status 和 git diff；
3. 不执行 reset、clean 或覆盖；
4. 交给主聊天决定如何把当前状态转移到任务分支；
5. 整理后让 main 回到只包含集成提交的状态。

“主线任务”只是当前检出的分支，不代表 Agent 会自动和其他聊天协同。

## Git 隔离不了的共享资源

Git 只能隔离文件和提交。本项目正式服务端口是 17865，还有正式运行目录、配对码、配置、浏览器资料和 GPU 资源。

任务 Agent 可以运行单元测试、夹具测试、随机端口模拟服务，并把临时产物写入自己的 work/<任务名> 或系统临时目录。

任务 Agent 默认不能从任务 worktree 启动或停止正式 start.ps1/stop.ps1，不能连接正式配对码，不能并行运行真实账号翻译、GPU ASR 或正式 Chrome 集成测试。正式服务和真实浏览器验证由主聊天安排独占时段。

以后如果需要多实例真实测试，必须另立任务，先验证端口、运行目录、服务地址、浏览器资料和 GPU 调度全部隔离。只创建 worktree 不会自动解决共享资源冲突。

## Token 节省规则

1. 同一个任务尽量使用同一个聊天；不要每个小修改都新开聊天。
2. 新聊天只提供实际路径、分支、目标、文件责任、验收条件和禁止事项，让 Agent 从磁盘读取项目文件。
3. 局部修改先运行针对性测试，合并后再运行完整 npm test。
4. 正式浏览器、服务和 GPU 测试集中在主聊天的验收阶段执行。
5. 要求 Agent 返回结构化短报告，不要把完整日志复制进聊天；需要细节时读取指定日志文件。
6. 只有独立目标才并行；如果两个任务频繁改同一文件或共享同一服务，串行通常更省 token。

## 合并流程

任务完成后，主聊天先检查：

~~~powershell
git switch main
git status --short --branch
git diff main...fix/subtitle-layout --stat
git diff main...fix/subtitle-layout
~~~

确认后合并：

~~~powershell
git merge --no-ff fix/subtitle-layout
npm test --prefix outputs/youtube-zh-assistant
git status --short --branch
~~~

--no-ff 保留任务合并节点，便于回溯一项任务何时进入产品。冲突要结合两边业务意图解决，不能盲目全部采用当前分支或全部采用对方分支。合并后必须在合并结果上重新测试。

## 发布和回退

只有主聊天在 main 上发布。任务 Agent 不改正式版本号，不生成最终安装包，不同步独立插件目录，不重启正式服务。

发布顺序仍然是：合并任务、更新版本记录和 CHANGELOG、提交并确认 main 干净、运行 node work/package-release.mjs --check、完成验证、生成并校验 ZIP/RAR、保存证据、创建不可覆盖标签、执行 tools/backup-git.ps1，最后按现有安全脚本处理正式服务和插件重载。

已经合并的错误改动使用新的撤销提交：

~~~powershell
git revert <错误提交号>
~~~

查看旧版代码使用独立 detached worktree，不要在正式目录随意切换：

~~~powershell
git worktree add --detach E:\YouTube中文插件开发-worktrees\inspect-047 v0.4.7
~~~

Git bundle 只包含已提交历史，不包含安装包、运行配置、配对码、密钥、模型和缓存；这些资料需要单独备份。
